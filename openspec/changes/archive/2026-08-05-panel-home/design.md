## Context

El sitio público Astro (apps/web/) completó su Fase A (bootstrap) y ya integra cuatro componentes UI en la home vía `Layout.astro` + `index.astro` (en este orden DOM): `TopHeader.astro` (utility bar archivada en `2026-08-02-top-header`), `Header.astro` (header principal con navegación + CTA archivado en `2026-08-02-site-header`), `SearchForm.astro` (barra de búsqueda archivada en `2026-08-04-search-form`) y `HeroBanner.astro` (hero del home archivado en `2026-08-04-banner-home`). El layout actual produce el orden: `<TopHeader /> → <Header /> → <div role="search">` (SearchForm) → `<slot />` de `index.astro` donde vive `<HeroBanner />`.

La imagen de referencia `docs/design/components/PanelHome.png` muestra la franja de "about / trust signals" que va inmediatamente debajo del hero:
- **Mitad izquierda** (fondo teal, mismo `#14B8A6` del token `--color-brand-teal` ya creado en `globals.css` para el CTA primario del HeroBanner): eyebrow "DESDE 1979" (uppercase, blanco), headline "Más de 40 Años de Liderazgo en la Medición y Control de Fluidos" (blanco, bold), párrafo descriptivo (blanco con opacidad reducida) y un CTA "SOLICITAR ASESORÍA TÉCNICA" navy sólido (fondo `brand-navy`, texto blanco).
- **Mitad derecha** (fondo blanco): grid 2×2 con 4 estadísticas — "40+ / AÑOS DE EXPERIENCIA EN LA INDUSTRIA", "30.000+ / EQUIPOS Y SOLUCIONES IMPLEMENTADAS", "5+ / MARCAS GLOBALES REPRESENTADAS", "9+ / LÍNEAS DE SOLUCIONES INDUSTRIALES". Cada celda tiene el value grande (navy, bold) y el label pequeño debajo (uppercase, gris).

El change archivado `banner-home` declaraba como Non-Goal explícito un `stats-strip` futuro (franja inferior con estadísticas debajo del hero). Este `PanelHome` **reemplaza y extiende** ese Non-Goal: en vez de una franja monolítica con stats, es una composición horizontal de dos mitades diferenciadas (copy+CTA | stats) y, además, se solapa parcialmente sobre el hero existente (~50% dentro del hero, ~50% debajo).

Decisiones confirmadas con el cliente (preguntas previas respondidas):
- **Posición**: Solapado parcialmente sobre el `HeroBanner` existente (50% sobre / 50% debajo).
- **Color del fondo izquierdo**: Reutilizar el token `--color-brand-teal` existente (`#14B8A6`); NO crear un nuevo token.
- **Datos de las estadísticas**: Hardcoded en `lib/config/panel-home.ts` (mismo patrón que `HERO_BANNER_CONTENT` y `NAVIGATION_ITEMS`).
- **Href del CTA**: `/contacto` (mismo destino que el CTA secundario "ESCRÍBENOS" del HeroBanner).
- **Cobertura de tests**: Completa — unit de config + AstroContainer + snapshot + E2E Playwright.

## Goals / Non-Goals

**Goals:**
- Componente `PanelHome.astro` presentacional puro (dumb): recibe `eyebrow`, `headline`, `description`, `cta`, `stats` por props; sin fetching ni estado de dominio, sin leer `import.meta.env` directamente
- Tipos TypeScript estrictos (`PanelHomeProps`, `PanelStat`, `PanelCta`) en `lib/types/panel-home.ts`
- Config hardcoded `PANEL_HOME_CONTENT` con el copy del panel, el CTA (`SOLICITAR ASESORÍA TÉCNICA` → `/contacto`) y las 4 estadísticas en `lib/config/panel-home.ts` (mismo patrón que `HERO_BANNER_CONTENT`, `NAVIGATION_ITEMS` y `CATEGORY_OPTIONS`)
- Solapamiento parcial sobre el `HeroBanner`: el `<section>` del PanelHome usa negativo `margin-top` (ej. `-mt-16 md:-mt-24`) y `position: relative` con `z-index` mayor que el HeroBanner, de modo que la mitad superior del panel queda dentro del área visual del hero y la mitad inferior queda debajo. No se modifica el HeroBanner. El solapamiento es puramente visual (CSS) y no rompe la legibilidad del hero (validado por E2E de contraste y layout)
- Layout responsivo: mobile (< 1024px) — las dos mitades se apilan verticalmente (teal arriba, blanco abajo), cada mitad full-width; desktop (>= 1024px) — grid de 2 columnas lado a lado, cada mitad 50% del ancho
- Grid interno de la mitad derecha: `grid-cols-2` siempre (2×2), 4 celdas iguales con padding consistente. En mobile (< 1024px) NO se convierte en grid de 1 columna, se mantiene 2×2 (las cifras son cortas y cabe bien en pantallas pequeñas; se valida con E2E a 320px)
- Accesibilidad: el headline del panel es `<h2>` (NO `<h1>`; el único `<h1>` de la home lo aporta el HeroBanner y no se duplica). El eyebrow es un `<span>` o `<p>` con clases uppercase, no un heading. El CTA es `<a href="/contacto">` focusable. Las celdas de stats usan `<div>` semánticos (no headings) para no inflar el outline del documento
- Contraste WCAG AA: el CTA navy (`#1B2A4A`) sobre fondo teal (`#14B8A6`) tiene ratio de contraste ~5.9:1 (validado en E2E); el texto blanco sobre teal tiene ratio ~2.8:1 — los grandes (headline) cumplen AA Large (>= 3:1), pero el párrafo descriptivo con opacidad reducida puede no cumplir AA Normal; se valida en E2E y se ajusta opacidad a `text-white/90` o `text-white` si es necesario antes de archivar
- Tests Vitest (unit de `PANEL_HOME_CONTENT` shape + AstroContainer + snapshot) y E2E Playwright (desktop/mobile/contraste/solapamiento/accesibilidad)
- Integración en `index.astro`: `<HeroBanner {...HERO_BANNER_CONTENT} />` seguido de `<PanelHome {...PANEL_HOME_CONTENT} />` dentro del `<slot />` del `<Layout>`. El orden DOM se mantiene: `TopHeader → header → div[role="search"] → section(hero) → section(panel)`

**Non-Goals:**
- NO se modifica `HeroBanner.astro` ni su spec archivada — el solapamiento visual se implementa 100% en el `PanelHome.astro` (negative margin-top, `relative`, `z-index`) y en `index.astro` (orden del render). El HeroBanner sigue produciendo exactamente el mismo HTML que antes
- NO se modifica `Layout.astro` — el `PanelHome` se renderiza vía el `<slot />` de `index.astro`, al igual que el `HeroBanner`. El Layout sigue produciendo el orden DOM `TopHeader → Header → SearchForm → slot`
- NO se modifica `SearchForm.astro`, `Header.astro`, `TopHeader.astro` ni sus specs archivadas
- NO se carga contenido desde Firestore/CMS — el copy y los 4 stats son hardcoded en `lib/config/panel-home.ts` por consistencia con el resto del sitio (SGS, cualquier cambio requiere rebuild). El change futuro `contentful-from-cms` reemplazará el contenido inyectándolo vía props sin tocar el componente
- NO se añaden animaciones, parallax, counters animados ni intersection-observer reveals al panel — comportamiento estático
- NO se añade un segundo CTA — solo "SOLICITAR ASESORÍA TÉCNICA" (navy) como en la imagen de referencia
- NO se añaden stats adicionales más allá de los 4 mostrados en la imagen de referencia (40+, 30.000+, 5+, 9+)
- NO se implementa una sección de testimonios ni partners logos — fuera de scope (agenda como change futuro `trust-testimonials` si se requiere)
- NO se implementa el cambio de variante del SearchForm ("SearchForm sobre hero oscuro") que estaba como Non-Goal del `banner-home` — sigue pendiente como change futuro `search-form-variants`. Este change no introduce variantes del SearchForm

## Decisions

1. **Dumb presentational component**: `PanelHome.astro` no hace fetching, no lee `import.meta.env`, no contiene lógica de negocio no trivial. `apps/web/src/pages/index.astro` importa `PANEL_HOME_CONTENT` de `lib/config/panel-home.ts` y se lo pasa spread al componente: `<PanelHome {...PANEL_HOME_CONTENT} />`. Cumple SRP de `frontend-standards.md` § "Principios de Diseño — Astro" (srp-astro). Alternativa considerada: leer el copy desde `import.meta.env.PANEL_*` con defaults (similar a `getSearchFormConfig()`) — descartada porque los stats son contenido editorial, no configuración; el fetch dinámico desde CMS entra en un change posterior `contentful-from-cms`.

2. **Grid principal `grid-cols-1 lg:grid-cols-2`**: la composición horizontal de dos mitades se logra con un grid CSS de Tailwind `grid grid-cols-1 lg:grid-cols-2`. En mobile (< 1024px) las dos mitades se apilan verticalmente (teal arriba, blanco abajo, cada una full-width); en desktop (>= 1024px) aparecen lado a lado, cada una 50% del ancho. El breakpoint es `lg` (1024px), no `md` (768px), porque el grid 2×2 interno de la mitad derecha necesita espacio horizontal suficiente para no romper visualmente. Alternativa considerada: `md:grid-cols-2` con `grid-cols-1` en mobile — descartada porque a 768px las 2 celdas del grid interno quedan demasiado estrechas para el value "30.000+".

3. **Grid interno de stats siempre `grid-cols-2`**: la mitad derecha usa `grid grid-cols-2 gap-x-8 gap-y-12 p-8 md:p-12` SIEMPRE, incluso en mobile (< 1024px). Las 4 celdas se disponen en 2×2. Alternativa considerada: `grid-cols-1 md:grid-cols-2` (apilar en mobile) — descartada porque las cifras son cortas (40+, 30.000+, 5+, 9+) y caben bien en 2 columnas a 320px; además la imagen de referencia muestra explícitamente el grid 2×2. Se valida con E2E a 320px que las celdas no se cortan ni rompen.

4. **Solapamiento sobre HeroBanner vía `negative margin-top` + `relative` + `z-index`**: el `<section>` del PanelHome lleva `relative -mt-16 md:-mt-24 lg:-mt-32 z-10`. El HeroBanner tiene `relative` (heredado de la implementación actual) pero sin `z-index` explícito; al asignar `z-10` al PanelHome, este aparece encima del hero. La magnitud del margin negativo es ~50% del padding vertical del hero (`py-16 md:py-24` del HeroBanner → `-mt-16 md:-mt-24`), de modo que la mitad superior del panel queda dentro del área visual del hero. Alternativa considerada: usar `position: absolute` con `top: -Xpx` — descartada por sacar el panel del flow normal y romper el layout en mobile. Alternativa considerada: trasladar el PanelHome dentro del `<section>` del HeroBanner — descartada porque violaría el Non-Goal "NO se modifica HeroBanner.astro" y el SRP (el HeroBanner dejaría de ser dumb y aislado). Alternativa considerada: usar `margin-block-start` con CSS custom — descartada por usar utilidades Tailwind estándar (consistencia con HeroBanner y SearchForm).

5. **CTA navy sobre teal, no teal sobre teal**: el CTA "SOLICITAR ASESORÍA TÉCNICA" usa `bg-brand-navy text-white hover:bg-brand-navy-light`, NO `bg-brand-teal` (que chocaría visualmente con el fondo teal del panel). Esto desbloquea la Regla de Diseño de "un solo `bg-brand-teal` por bloque visual" y mantiene la jerarquía: el teal del fondo es el color "fuerte" del bloque, el navy del CTA es el color "de acción". Alternativa considerada: CTA outline blanco (`border-2 border-white text-white hover:bg-white hover:text-brand-teal`, mismo patrón que el CTA secundario del HeroBanner) — descartada porque la imagen de referencia muestra claramente un CTA sólido navy, no outline.

6. **`<h2>` para el headline del panel, sin `<h3>` ni nuevo `<h1>`**: el headline "Más de 40 Años de Liderazgo..." se renderiza como `<h2 class="text-2xl md:text-3xl lg:text-4xl font-bold text-white">`. No es `<h1>` (la home tiene un solo `<h1>` y lo aporta el HeroBanner, regla SEO on-page). No es `<h3>` (no hay `<h2>` previo en el documento entre el `<h1>` del hero y este headline; saltarse niveles rompe el outline). El eyebrow "DESDE 1979" es un `<span>` uppercase (`<span class="block text-sm font-bold uppercase tracking-wider text-white/80">`), no un heading. Alternativa considerada: eyebrow como `<h3>` — descartada por inflar el outline del documento sin aportar jerarquía real (es texto decorativo).

7. **Stats como `<div>` con `<p>` anidados, sin headings**: cada celda de stat es `<div class="text-center md:text-left"><p class="text-3xl md:text-4xl font-bold text-brand-navy">{value}</p><p class="mt-2 text-xs md:text-sm uppercase tracking-wide text-gray-600 max-w-">{label}</p></div>`. Los valores NO son `<h3>` ni `<h4>`: son datos puntuales, no secciones del documento. Usar headings inflaría el outline del documento y rompería la jerarquía (`<h1>` hero → `<h2>` panel → `<h3>` stats no aporta nada semántico). Alternativa considerada: stats como `<dl>` con `<dt>`/`<dd>` — descartada por over-engineering para 4 cifras; se mantiene `<div>` simple semántico.

8. **`PANEL_HOME_CONTENT` como `Readonly<PanelHomeProps>` en `lib/config/panel-home.ts`**: mismo patrón que `HERO_BANNER_CONTENT` en `hero-banner.ts`. Permite al cliente ajustar copy, href del CTA y los 4 stats en un solo archivo sin tocar el componente. Alternativa considerada: separar `PANEL_COPY` y `PANEL_STATS` en dos constantes — descartada por añadir dos exports sin valor (el componente recibe una sola props bag).

9. **`PanelCta` reutiliza el shape de `HeroCta` pero vive en su propio archivo**: el tipo `PanelCta` se define en `lib/types/panel-home.ts` con el mismo shape que `HeroCta` (`{ readonly label: string; readonly href: string; readonly variant: 'primary' | 'secondary' }`). NO se importa `HeroCta` desde `hero-banner.ts` para evitar acoplamiento entre changes (si el HeroBanner evoluciona su `HeroCta` en un change futuro, el PanelHome no debe romper). El DRY se pierde pero se gana estabilidad del contrato. Alternativa considerada: importar `HeroCta` — descartada por acoplamiento cross-change. Alternativa considerada: extraer `Cta` a `lib/types/cta.ts` compartido — descartada porque el change `contentful-from-cms` futuro podría hacer que cada componente reciba sus CTAs con shapes distintas (ej. el CTA del panel podría aceptar `subRoute` o `formTarget`); mantenerlos separados evita un refactor futuro.

10. **Ajuste de opacidad del párrafo descriptivo para cumplir WCAG AA**: el párrafo descriptivo sobre fondo teal se renderiza con `text-white/80` inicialmente (`text-white/80 max-w-md`). En E2E se calcula el ratio de contraste calculado de `#CBD5E1` (blanco 80% sobre teal `#14B8A6`); si no llega a 4.5:1 (AA Normal), se sube a `text-white/90` o `text-white`. Se valida en la sección 4 de tasks (E2E de contraste). Alternativa considerada: usar `text-white` siempre — descartada porque reduce la jerarquía visual (el headline y el párrafo quedarían con el mismo peso). **POST-APPLY UPDATE (2026-08-04)**: los E2E confirmaron que el ratio de contraste texto-blanco-sobre-teal cumpla AA es ~2.49:1 (NO cumple AA Large >= 3:1 ni AA Normal >= 4.5:1). El cliente indicó que rollingá una revisión global del sistema de diseño en un change futuro, así que las tasks 4.13 y 4.14 se marcan como known-TODO al archivar (mismo patrón que las Open Questions del `banner-home`). El fix específico queda agenda para el change `design-system-revision` que debe ajustar el token `--color-brand-teal` (o introducir un `--color-brand-teal-dark` para el fondo del panel) sin necesidad de tocar el componente.

11. **Solapamiento sobre HeroBanner sin tapar el headline del hero (POST-APLY UPDATE 2026-08-04)**: originalmente se decladó `-mt-16 md:-mt-24 lg:-mt-32` (igando a 50% del padding vertical del hero). En pruebas E2E se observó que el panel tapaba parte del contenido inferior del HeroBanner (el `<h2>`subtitle y los CTA). Ajuste: reducir el solapamiento a `-mt-8 md:-mt-12 lg:-mt-16` (aproximadamente 25% del padding del hero) para que el panel entre en el aire inferior del hero sin tocar el contenido. El test E2E 4.8 ya valida esto en 320px / 768px / 1024px / 1440px. Alternativa considerada: eliminar el solapamiento (margin-top: 0) — descartada porque el cliente confirmo explícitamente que quiere el solapamiento visual; solo se reduce la magnitud para no tapar contenido.

12. **Ancho del panel acotado al `.container` (no full-width) (POST-APPLY UPDATE 2026-08-04)**: originalmente el `<section>` exterior conteni­a el grid `grid-cols-1 lg:grid-cols-2` directamente, de modo que el panel visual ocupaba el 100% del viewport. Con el solapamiento sobre el hero, la anchura full-width hacia difficil interpretar que el panel "flota" sobre el banner. Ajuste: envolver el grid principal en un `<div class="container mx-auto px-4 sm:px-6 lg:px-8">` dentro del `<section>`, de modo que el panel visual (teal+blanco) queda acotado a `max-w-7xl` y centrado horizontalmente, con el fondo del hero fluyendo a ambos lados si el viewport supera `7xl` (1280px+). Esto coincide con el ancho del SearchForm, que usa el mismo `.container` utility (`apps/web/src/styles/globals.css`), reforzando la sensacion de "componente que flota solapado entre el Banner principal y la siguiente sección". El `<section>` exterior sigue full-width para no romper otros tests de bounding-box vertical y el orden DOM establecido en la task 4.11. Alternativa considerada: acotar el `<section>` exterior a `container` también — descartada porque entonces el solapamiento vertical medido por el E2E 4.7 seguiría걸 overflow al px borde pero serí­a consistente con el resto del site; el wrapper interno en `container` preserva la capacidad futura de anadir un fondo decorativo full-width al `<section>` (tope futuro, no打破 E2E). Alternativa considerada: usar `max-w-7xl` directamente sin `container` — descartada porque `container` ya encapsula `mx-auto` + `px-*` responsive, manteniendo el principio DRY del sitio.

## Risks / Trade-offs

- **Risk**: El solapamiento sobre el HeroBanner puede romper la legibilidad del headline del hero en ciertos viewports (el panel cubre parte del hero) → **Mitigation**: la magnitud del margin negativo (`-mt-16 md:-mt-24 lg:-mt-32`) está calibrada para cubrir ~50% del padding inferior del hero, no el headline. El hero tiene `py-16 md:py-24` de aire vertical, por lo que el panel entra en ese espacio vacío, no sobre el texto. Tests E2E en 320px / 768px / 1024px / 1440px verifican que el `<h1>` del hero sigue siendo visible y no se solapa con el panel.

- **Risk**: El CTA navy sobre fondo teal puede no cumplir WCAG AA → **Mitigation**: ratio calculado de `#1B2A4A` (navy) sobre `#14B8A6` (teal) ≈ 5.9:1, superior a 4.5:1 (AA Normal) y a 3:1 (AA Large). El texto del CTA es blanco bold sobre navy, ratio `#FFFFFF` sobre `#1B2A4A` ≈ 11.4:1. Validado en E2E de contraste.

- **Risk**: El texto blanco del eyebrow/párrafo sobre teal puede no cumplir AA Normal → **Mitigation**: el eyebrow es bold uppercase short (AA Large aplica, >= 3:1, cumple con ~2.8:1 — ajustable a `text-white/90` si se requiere). El párrafo descriptivo se valida en E2E y se sube de `text-white/80` a `text-white/90` o `text-white` si es necesario. El headline `<h2>` es bold y grande (>= 18pt), AA Large aplica (>= 3:1).

- **Risk**: Cambiar el layout del `index.astro` puede romper el snapshot del HeroBanner existente → **Mitigation**: el snapshot del HeroBanner vive en `HeroBanner.test.ts.snap` y se renderiza en aislado vía `AstroContainer` sin el `Layout` ni la página; por construction no se ve afectado por añadir `<PanelHome />` después. Sin embargo, el snapshot del home completo (`index.astro` renderizada completa, si existe) se regenera como parte de este change (regresión intencional documentada).

- **Risk**: En mobile (< 1024px) el solapamiento sobre el hero puede empujar el panel demasiado arriba y solapar el `<h1>` del hero → **Mitigation**: el margin negativo en mobile se reduce a `-mt-16` (más pequeño que el del hero `py-16`), de modo que el panel ocupa solo ~50% del espacio del aire inferior del hero. Validado en E2E a 375px que el `<h1>` "Innovación que Fluye" sigue siendo visible por encima del panel.

- **Risk**: El grid 2×2 de stats puede romper en pantallas muy pequeñas (< 360px) si el value "30.000+" no cabe en media columna → **Mitigation**: tests E2E a 320px validan que las celdas no se cortan; se puede ajustar `text-3xl` a `text-2xl` en mobile si es necesario (un solo punto de cambio en el componente).

- **Trade-off**: Hardcoded del contenido (copy + stats) vs fetch desde CMS/Firestore → simplicidad y tipos estrictos ahora; el change `contentful-from-cms` futuro lo reemplaza inyectando el contenido vía props sin tocar el componente (mismo trade-off aceptado en `banner-home`).

- **Trade-off**: `PanelCta` duplica el shape de `HeroCta` (DRY) → se acepta para evitar acoplamiento cross-change; ver Decisión 9 para el rationale completo.

- **Trade-off**: Solapamiento visual via negative margin (CSS) vs componentizar el hero+panel en un solo componente contenedor → se elige negative margin para respetar el Non-Goal "NO se modifica HeroBanner.astro" y el SRP; el contenedor unificado se considera en un change futuro `hero-panel-composition` si el solapamiento necesita más control.

## Migration Plan

- No requiere migración de datos ni cambios de API (`docs/api-spec.yml` invariante).
- Deploy: build SSG estándar (misma pipeline que Fase A). El `PanelHome` nuevo + el `index.astro` actualizado (con `<PanelHome />` añadido después del `<HeroBanner />`) entran juntos en un solo cambio. La pipeline existente (`npm run build`, `npm run typecheck`, `npm run lint`, `npm run test`, `npm run test:smoke`) valida todo.
- Rollback: revertir el commit del change `panel-home` — `index.astro` vuelve a renderizar solo `<HeroBanner {...HERO_BANNER_CONTENT} />` dentro del `<Layout>`, los archivos nuevos (`PanelHome.astro`, `lib/types/panel-home.ts`, `lib/config/panel-home.ts`, tests asociados) se eliminan. No hay efectos en `HeroBanner.astro`, `Layout.astro`, `SearchForm.astro`, `Header.astro`, `TopHeader.astro` ni sus specs.
