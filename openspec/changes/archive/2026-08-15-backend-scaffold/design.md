## Context

`apps/backend` es un scaffold vacío: solo existe el `package.json` (declaración de dependencias NestJS 10, firebase-admin 12, jest/ts-jest, eslint, typescript, class-validator/transformer, throttler) y un `node_modules` parcial (únicamente `@types/node`, leftover de un `npm install` incompleto o del hoisting del workspace root). No hay `src/`, ni `tsconfig.json`, ni `nest-cli.json`, ni `jest.config.js`, ni Dockerfile, ni `.env`, ni README. Ningún change archivado (los 24 en `openspec/changes/archive/`) tocó el backend: todos son del sitio Astro (`apps/web`) y documentan explícitamente "no se toca `apps/backend/*`".

El contrato está completo en `docs/api-spec.yml` (endpoint `/health` declarado en líneas 502-516 con respuesta `{ "status": "ok" }`) y en `docs/backend-standards.md` (stack Node 20/NestJS 10+/firebase-admin 12, coverage 90%, estructura Clean Architecture por módulo, umbrales SOLID medibles: 300 líneas/archivo, complejidad 10, ≤3 params por constructor, profundidad herencia 2). Los templates de lint SOLID backend ya existen en `templates/ci/eslintrc.backend.js` y `templates/ci/.dependency-cruiser.js` (regla `no-infra-from-domain`), pero no están copiados a `apps/backend/`; el target `make solid-lint` del Makefile tiene una rama backend condicional (`if [ -d src ]`) que hoy está inactiva por la ausencia de `src/`.

El `package.json` raíz exige `engines.node >= 22.12.0`, mientras que `docs/backend-standards.md` menciona Node 20. **Decisión**: este change se adhiere a `engines.node` ya declarado (Node 22) — el guard del `package.json` es el punto único de configuración; corregir el estándar docs → Node 22 queda fuera de alcance (change docs-only aparte, no hace falta para este ciclo).

Este change es el primero de una serie de 6: `backend-scaffold` → `backend-firebase-config` → `backend-commons` → `backend-categorias` → `backend-subcategorias` → `backend-productos`. Sin este esqueleto runnable, ninguno de los siguientes puede empezar.

## Goals / Non-Goals

**Goals:**
- `apps/backend` compilable (`npm run build` → `dist/main.js`), arrancable (`npm start`), linteable (`npm run lint` verde), testeable (`npm test` verde con coverage ≥ 90%), typecheck verde (`npm run typecheck`).
- Estructura base de proyecto NestJS: `src/main.ts` (bootstrap), `src/app.module.ts` (root module), `src/app.controller.ts` + `src/app.service.ts` con el endpoint `GET /health` → `{ "status": "ok" }` declarado en `docs/api-spec.yml`.
- Configs TS estrictas (`tsconfig.json` strict mode, target ES2022, paths `@/*` → `src/*`, experimentalDecorators + emitDecoratorMetadata para NestJS DI), `tsconfig.build.json` (excluye specs), `nest-cli.json` (sourceRoot `src`).
- Configs Jest: `jest.config.js` con ts-jest preset y thresholds de coverage 90% globales (statements/branches/functions/lines) conforme a `docs/backend-standards.md` § Testing backend; `jest-e2e.json` para tests e2e separados de unitarios.
- Lint SOLID activo en el backend: `.eslintrc.cjs` adaptado de `templates/ci/eslintrc.backend.js` (max-lines 300, complexity 10, sonarjs cognitive-complexity 10, `@typescript-eslint` recommended) y `.dependency-cruiser.js` copiado de `templates/ci/.dependency-cruiser.js` (regla `no-infra-from-domain` — guard preventivo para los changes siguientes aunque aquí no haya `domain/` todavía).
- `Dockerfile` multi-stage funcional (build → runtime slim) que produce una imagen arrancable con `node dist/main.js`.
- `README.md` del módulo backend con: descripción 1-línea, requisitos, setup 3 pasos, variables env, comandos clave (dev/test/lint/build).
- `.env.example` placeholder (`PORT=3000`); variables Firebase/CORS/Throttler entran en changes posteriores.
- `.gitignore` ignora `dist/`, `coverage/`, `.env`, `*.local`.
- Dependencias del `package.json` efectivamente instaladas (vía `npm install` desde workspace root para que el hoisting del monorepo resuelva correctamente).

**Non-Goals:**
- NO se implementa ningún módulo de dominio (categorias, subcategorias, productos, usuarios, cotizaciones) — entran en changes posteriores.
- NO se incluye Firebase / firebase-admin initialization (entra en `backend-firebase-config`).
- NO se incluye Auth Guard, verificación JWT, Custom Claims, CORS, ThrottlerModule, filtro de excepciones con envelope `{ data, error, meta }`, ni helpers de paginación — entran en `backend-commons`.
- NO se reescribe el `.env.example` raíz (postgres/S3/JWT propio stale) — se alinea en `backend-firebase-config` con las variables reales de Firestore/Auth/Storage.
- NO se toca `docs/api-spec.yml`, `docs/data-model.md`, ni ningún archivo de `apps/web` o `apps/admin`.
- NO se instrumenta la regla `no-infra-from-domain` para exigir la existencia de carpetas `domain/` o `infrastructure/` (no hay módulos de dominio todavía); `.dependency-cruiser.js` se copia como guard preventivo y se activará real cuando `backend-categorias` cree `domain/`.
- NO se arreglan las ~90 vulns de `npm audit` en cadena webpack de `@nestjs/cli` (pre-existentes, documentadas en `2026-08-05-design-system-revision/tasks.md` 8.10; requieren upgrade breaking → change futuro).

## Decisions

1. **Node 22 como runtime canónico.** `package.json` raíz declara `engines.node >= 22.12.0` (única fuente canónica de versión). El Dockerfile usa `node:22-slim` como base runtime y `node:22` como base de build. El estándar `docs/backend-standards.md` menciona Node 20 (stale del template Specboot); no se corrige en este change (fuera de alcance, seria change docs-only). Alternativa considerada: bajar `engines.node` a 20 para alinearse con docs — descartada porque rompería el guard activo del `package.json` raíz y los 24 changes ya archivados corren en Node 22.
2. **`npm install` desde workspace root, no desde `apps/backend`.** El `package.json` raíz define `workspaces: ["apps/*"]`. Instalar desde `apps/backend` directo generaría un `node_modules` local duplicado y rompería el hoisting. `npm install` (sin `--workspace`) desde la raíz instala todas las deps de todos los workspaces y deja un único `node_modules` hoisted. Alternativa considerada: `npm install --workspace=@riff/backend` — equivalente, se usa la forma raíz por costumbre del monorepo.
3. **`tsconfig.json` strict + ES2022 + NestJS DI metadata.** `strict: true`, `target: "ES2022"`, `module: "CommonJS"`, `experimentalDecorators: true`, `emitDecoratorMetadata: true` (necesarios para que NestJS DI funcione), `outDir: "./dist"`, `rootDir: "./src"`, `baseUrl: "./"`, paths `@/*` → `src/*`. `tsconfig.build.json` extiende `tsconfig.json` y añade `exclude: ["**/*.spec.ts", "**/*.e2e-spec.ts"]` para que `nest build` no empaquete tests. Alternativa considerada: usar `tsconfig.json` directo para build (sin el `.build`) — descartada, es el patrón canónico NestJS CLI y permite tener specs excluidas del bundle de producción.
4. **`/health` SIN prefijo `/api/v1`.** `docs/api-spec.yml` declara la ruta como `/health` (línea 502), no `/api/v1/health` (fuera del bloque versionado). La API versioning por prefijo (`/api/v1`) se configura en `backend-commons` (SetGlobalPrefix) o en cada módulo; en este change, `main.ts` no setea prefijo global y `/health` queda en la raíz. Alternativa considerada: setear `/api/v1` ahora y poner `/health` debajo → rompe el contrato del spec (`/health`, no `/api/v1/health`). Alternativa considerada: dejar `/health` sin prefijo para siempre y configurar `/api/v1` solo en módulos de dominio → inconsistente con global prefix típico de NestJS, descartada. **Decisión:** este change NO setea prefijo global; `backend-commons` decide en su design si el prefijo `/api/v1` es global (con `/health` excluido) o por-módulo.
5. **`AppController` + `AppService` dummy — NO un módulo `health/` todavía.** El endpoint `/health` se implementa en un `AppController` + `AppService` raíz (mínimos). No se crea módulo `health/` dedicado porque `/health` reporta solo `{ status: 'ok' }`; cuando `backend-commons` extienda `/health` para reportar conexión Firestore/Storage, ese change refactoriza el `AppService` a un `HealthModule` con `HealthIndicator`s de NestJS (`@nestjs/terminus` — dependency que se añade en ese change). Alternativa considerada: usar `@nestjs/terminus` desde ya — descartada porque añade una dependencia que solo es útil en `backend-commons` y porque el spec actual solo pide `{ status: 'ok' }`.
6. **Jest thresholds 90% GLOBALES, no por-archivo.** `jest.config.js` declara `coverageThreshold: { global: { statements: 90, branches: 90, functions: 90, lines: 90 } }`. Con solo `AppController` + `AppService` + `main.ts` (que NestJS excluye de coverage típicamente), los archivos cubribles son Minúsculos y 90% es fácilmente alcanzable. Alternativa considerada: thresholds por-archivo — descartada, frágil cuando los módulos crecen; los umbrales por-archivo se evalúan en `backend-commons` cuando se decide cobertura por módulo.
7. **Tests e2e separados de unitarios vía `jest-e2e.json` + script dedicado.** `package.json` actual ya declara `test: 'jest'` (corre specs `*.spec.ts`) y `test:smoke: 'jest --testPathPattern=smoke'`. Se añade `test:e2e: 'jest --config jest-e2e.json'` al `package.json` (test e2e del scaffold: levanta la app con `Test.createTestingModule` + `INestApplication` y hace `GET /health`). Los e2e del scaffold NO levantan HTTP real (no en este change); el primer e2e HTTP real (con `supertest` + listener en un puerto efímero) entra en `backend-commons` cuando se añade `supertest` como dep. Alternativa considerada: añadir `supertest` ahora — descartada, mantiene el cambio minimalista; el e2e del scaffold usa el `TestingModule` + `app.getHttpServer()` que NestJS testing expone sin `supertest`.
8. **`.eslintrc.cjs` copiado y adaptado desde `templates/ci/eslintrc.backend.js`.** El template ya declara los umbrales SOLID del estándar (max-lines 300, complexity 10, sonarjs cognitive-complexity 10, `@typescript-eslint/recommended` + `recommended-type-checked`). Se copia a `apps/backend/.eslintrc.cjs` y se ajustan rutas/parsers para que corra sobre `src/**/*.ts` del workspace backend. **NO se incluye el plugin de Prettier** (no hay `.prettierrc` aún; se decide su inclusión en un change posterior si el cliente la pide). Alternativa considerada: crear `.eslintrc.cjs` desde cero — descartada, el template ya está alineado con el estándar y validado por `solid-templates-test.sh`.
9. **`.dependency-cruiser.js` copiado como guard preventivo.** El template define la regla `no-infra-from-domain` (prohíbe a archivos de `domain/` o `application/` importar paquetes de infra: `firebase-admin`, `@nestjs/axios`, etc.). En este change no hay `domain/` todavía, así que la regla no se dispara — se copia para que esté activa el día que `backend-categorias` cree la primera carpeta `domain/`. Alternativa considerada: copiarlo en `backend-categorias` — descartada, mejor tener el guard desde el scaffold para no olvidarlo.
10. **Dockerfile multi-stage base.** Stage `build`: base `node:22`, `WORKDIR /app`, copia `package.json` + `package-lock.json` del workspace (el lockfile raíz), `npm ci --workspace=@riff/backend`, copia `src/` + configs, `npm run build`. Stage `runtime`: base `node:22-slim`, copia `dist/` + `node_modules/` (production deps only) desde el stage build, `EXPOSE 3000`, `CMD ["node", "dist/main.js"]`. **NOTA**: mover archivos de un monorepo npm workspaces a un Docker context requiere copiar el `package.json` raíz + el `apps/backend/package.json` (los dos) para que `npm ci --workspace` resuelva; se usa `.dockerignore` para excluir `node_modules/`, `dist/`, `coverage/` de otros workspaces. Si `npm ci` en Docker falla por el monorepo workspace, se documenta como fallback `npm install --omit=dev` en `apps/backend` directo (sin workspace). Alternativa considerada: Dockerfile que solo usa `apps/backend/package.json` como contexto raíz — descartada porque rompe el workspace; `npm ci --workspace` requiere el lockfile y `package.json` raíz.
11. **No añadir dependencias nuevas al `package.json`.** Todas las deps necesarias ya están declaradas (NestJS 10, firebase-admin 12, jest, ts-jest, eslint). El único añadido posible es `supertest` para e2e HTTP, pero se decide en `backend-commons`. Mantener el `package.json` invariante reduces el riesgo de tocar el lockfile.

## Risks / Trade-offs

- **Risk**: `npm install` requiere `--legacy-peer-deps` por conflictos entre Angular (workspace `apps/admin`) y NestJS peer deps. → **Mitigation**: ejecutar `npm install` (sin flags) primero; si falla con `ERESOLVE`, reintentar con `--legacy-peer-deps` y documentar en `README.md`. El uso de legacy-peer-deps es un trade-off temporal: cuando Angular suba a 21 (change futuro) y el peer conflict desaparezca, se quita el flag.
- **Risk**: ~90 vulns de `npm audit` (cadena webpack de `@nestjs/cli` 10, pre-existentes) pueden encender alertas de CI (`make audit`). → **Mitigation**: gap pre-existente documentado en `2026-08-05-design-system-revision/tasks.md` 8.10; no introducido por este change. El `make audit` CI falla solo si hay vulns a nivel `high`; se documenta en el `tasks.md` que esto queda fuera de alcance.
- **Risk**: El Dockerfile en monorepo workspaces es complejo (copiar dos `package.json` + lockfile para que `npm ci --workspace` funcione). → **Mitigation**: `.dockerignore` correcto + fallback documentado (`npm install --omit=dev` en `apps/backend` directo si workspace-fail). El deploy real del backend se evalúa en `backend-commons` o en `backend-categorias`; aquí solo se entrega un Dockerfile base funcional para build local.
- **Risk**: El `main.ts` que NO setea prefijo global puede dejar rutas sin `/api/v1` y romper el contrato de `docs/api-spec.yml` (donde los endpoints son `/api/v1/products`, etc.) si alguien implementa un módulo de dominio antes de `backend-commons`. → **Mitigation**: este change se documenta como NO apto para añadir módulos de dominio hasta que `backend-commons` configure el prefijo `/api/v1`. El `/health` sí está en la raíz y coincide con el spec.
- **Trade-off**:_thresholds 90% globales vs por-archivo → simplicidad en el scaffold; los por-archivo se evalúan en `backend-commons` cuando la base de código crezca.
- **Trade-off**: no usar `@nestjs/terminus` para `/health` ahora → dependency extra innecesaria para una respuesta `{"status":"ok"}`; el refactor a terminus entra en `backend-commons`.
- **Trade-off**: copiar `.dependency-cruiser.js` sin `domain/` presente → guard preventivo; si la regla tuviera un bug de config, el lint pasa de todas formas porque no hay archivos que cruisar. Re-armar la regla se valida en `backend-categorias`.

## Migration Plan

- No hay migración de datos (Firestore schemaless, sin `domain/` todavía).
- Deploy: este change no se deploya a staging solo — es fundación para el siguiente. El primer deploy del backend a staging ocurre cuando hay al menos un endpoint de dominio funcional (probablemente `backend-categorias`).
- Rollback: revertir el commit del change — `apps/backend` vuelve a ser un scaffold vacío (solo `package.json`); los 24 changes archivados del frontend no se afectan.
- `make solid-lint` del Makefile comenzará a ejecutar la rama backend (test/CI). Si el lint backend falla, bloquea CI; se valida que `npm run lint` sea verde antes del commit.

## Open Questions

- ¿El `main.ts` debe setear CORS global ya (aunque sea `*`) o esperar a `backend-commons` para configurar orígenes específicos (`ASTRO_SITE_URL`, `ANGULAR_ADMIN_URL`)? **Decisión**: defer a `backend-commons` — en este change el scaffold no hace CORS; el endpoint `/health` no necesita CORS para los smoke tests locales.
- ¿`/health` debe reportar uptime / timestamp / versión de la app además de `{"status":"ok"}`? `docs/api-spec.yml` solo muestra `{ "status": "ok" }`. **Decisión**: el backend solo devuelve `{"status":"ok"}` en este change; si el cliente quiere uptime/versión, se añade en `backend-commons`.
- ¿Se incluye `helmet` (seguridad HTTP headers) en este scaffold? **Decisión**: no; entra en `backend-commons` con CORS/Throttler para mantener fundaciones de seguridad agrupadas.
